# 設計判断の記録

## 位置付け

本書は重要な決定と理由を記録する。[product.md](./product.md) は思想、[requirements.md](./requirements.md) はユーザー向け仕様、[screens.md](./screens.md) は画面と遷移、[data_model.md](./data_model.md) は論理モデル、[db-implementation.md](./db-implementation.md) はDB実装設計を担う。

以下は2026-09-27の一連の決定を、後の補足を優先して整理した現行仕様。以前の「未決定」や撤回された案を有効な仕様として併記しない。今回は文書のみを更新し、コード・migration・DB・Storageは変更していない。

## 認証とプロフィール

認証はメール・パスワードとGoogle Account。Apple Accountは後の補足によりMVP対象外とする。S07は認証後の初回プロフィール入力と通常編集で共用する。表示名は必須・重複可、画像は任意。初回保存で本人のプロフィールを作る。限定公開の共有リンクからの閲覧には認証・初回入力を要求しない。

理由：明示された認証方法と、共通の初回入力フローに統一するため。メール確認等の詳細は未決定。

## 旅行の公開・権限

旅行の公開範囲は、非公開・限定公開・将来の一般公開を区別する。MVPで提供するのは非公開と限定公開で、初期値は非公開。変更は旅行作成者のみ。

| 公開範囲 | 非参加者の閲覧 | 提供時期 |
| --- | --- | --- |
| 非公開 (`private`) | 不可。写真の公開設定がtrueでも不可 | MVP・初期値 |
| 限定公開 (`unlisted`) | 共有リンクの閲覧条件を満たす人がログイン不要で閲覧 | MVP |
| 一般公開 (`public`) | 限定公開と区別した一般向け閲覧。検索・一覧等の具体的仕様は後日決定 | 将来。MVPでは選択・保存・閲覧許可しない |

限定公開は、これまでの共有リンクの議論に基づき「リンクを知る人が閲覧できる」として設計する。閲覧用リンクの期限・失効・再発行方法と発行操作の権限は未決定。参加用招待URLの24時間を閲覧リンクへ自動適用しない。共有リンクの閲覧でメンバー登録・編集権限は付与しない。

旅行を閲覧できる非参加者にも、写真は `itinerary_photos.is_public = true` のものだけを返す。この条件は限定公開・将来の一般公開で共通。非公開旅行の写真だけを単独公開することはない。メモ・参加者一覧・表示名・プロフィール画像・投稿者情報は返さず、人数のみ返す。

理由：MVPの限定公開と将来の一般公開をbooleanで混同しないため、旧 `trips.is_public` 案を `trips.visibility text NOT NULL DEFAULT 'private'` に置き換える。値名は技術上の命名。MVPのCHECKは `private / unlisted` に限定し、一般公開導入時に `public` を追加して認可・UIを拡張する。写真の `is_public` は維持する。既存データを別構造へ作り直す設計は避けるが、将来のmigrationが一切不要という意味ではない。

限定公開のトークン検証と、旅行の閲覧判定・写真のフィルタを分離する。閲覧用共有リンクと、24時間・複数人利用可能な参加用招待リンクを別の資格として扱う。詳細はDB実装設計の技術案を参照する。

S08はメンバー専用。C01のメモは単一の任意テキスト `itinerary_items.description` のままとする。旅行削除・招待は作成者のみで、作成者以外のメンバーは退出可能。作成者の退出・他者の強制退出・作成者移譲・メンバーroleは追加しない。

## 写真

- 写真は旅程アイテムに紐づき、1アイテムにつき最大5枚。旅行サムネイル・アバターは別管理。
- 初期値は非公開。`itinerary_photos.is_public boolean NOT NULL DEFAULT false` を維持する。
- メンバーなら誰でも追加・差し替え・削除できる。
- 任意の公開設定変更は旅行作成者のみ。
- 差し替えは作成者が行う場合も必ず非公開へ戻し、作成者が明示的に再公開する。

理由：公開済み写真を別画像へ置き換えて未確認の画像を公開しないため。通常メンバーによる差し替えに伴うfalseへの自動リセットは、公開状態の任意変更とは別操作とする。

DBでは枚数の同時登録競合を防ぎ、差し替えパスと公開リセットを同時に更新する。Storageでは新キーへアップロードして、古い公開URLに新画像を上書きしない。形式・容量・確定UI等は残件。

## 旅程・時間

`place` と `transportation` を1つの旅程として扱い、日付内の `sort_order` 順に表示する。時刻では並べ替えない。`place` は場所・その場所で行うこと・滞在中の行動を含み、独立した `action` は追加しない。`trip_days` やカテゴリ別詳細テーブルは使用しない。

内容入力は名前のみ必須。時間・メモ・写真・所要時間は任意。日付・カテゴリ・挿入位置は選択情報から保持し、内部の必須カラムをNULL可能にはしない。名前の空文字は不可、空白のみや文字数の詳細は未決定。

時間帯は朝・昼・おやつ・夕方・夜の5択。モデル・DDL案ではその文字列を保存値とする。正確な時刻はOS・ブラウザ標準の時刻入力を使う。表示の端末差は許容する。

| time_type | exact_time | time_period |
| --- | --- | --- |
| exact | NOT NULL | NULL |
| period | NULL | NOT NULL・5択のいずれか |
| none | NULL | NULL |

理由：名前だけで旅程を作れ、必要な項目だけ時間を補えるようにするため。時間の整合性と値域はDB CHECKで保証する。時刻指定方法を選択した場合は対応値が必要。

## 保存単位と排他

既存旅程の基本項目・順序はS05の「更新」で日単位保存する。既存アイテムのメモ・写真アップロードはC01内で即保存し、S05の更新を待たない。新規アイテム・メモ・写真は入力モーダルの「保存」で合わせて登録し、「キャンセル」では登録を確定しない。

未保存の並び替え中は本人も新規追加不可。先に日単位更新または並び替えの破棄を行う。並び替え中は対象日の別の並び替え・アイテム追加・削除・日付移動を禁止する。メモ・写真は並び替え中でも変更でき、同じメモ・同じ写真への変更は個別に競合を防ぐ。旅行削除・期間短縮では編集中のアイテムを消さないよう調整する。

理由：更新単位と新規挿入位置の混在を避けるため。即保存したメモや新規登録を、古い日単位更新や変更破棄で巻き戻さない。編集権は画面のボタンだけでなくDBで検証する。通信切断・期限切れ・別タブも扱う。DBとStorageの保存は原子的ではないため、部分失敗・再試行・清掃を設計する。

## 旅行期間短縮

旅程日は原則旅行期間内とし、MVPではアプリケーション側で検証する。別テーブルを読む単純なDB CHECKは使わない。

期間短縮で範囲外旅程がある場合、「期間外になった旅程は削除されます。よろしいですか。」と確認する。了承時に期間変更と範囲外旅程の削除を行う。キャンセル時はどちらも行わない。メモ・写真も削除対象となることを併記し、Storage画像は別途清掃する。

理由：勝手に日付を移動せず、利用者の確認後に新期間と旅程を整合させるため。確認後に削除対象が変わった場合は再確認する。

## 招待と参加

招待は作成者がS08から発行し、URLの有効期限は発行から24時間。参加確定時にも期限を検証する。参加確認画面は設けない。URLを開き、必要な認証・S07初回入力・参加登録を経てS03（旅行一覧・ホーム）へ遷移し、旅行が一覧へ追加される。

理由：閲覧用URLと編集権限を得る招待URLを区別し、重複する参加確認操作を増やさないため。未検証の自己加入は許可しない。単純なURLプレビューだけでは参加を確定せず、認証済みの処理から参加登録する。

同じ招待URLは有効期限内に複数人が利用できる。参加してもURLを消費・無効化しない。失効・転送可否・配布UIは未決定。

## 画面構成

S01・S02・S04・S06は独立ページ、S03・S05・S07もページ。S08・C01はモーダル、S09はS05の編集状態。S10は旅程上下の＋からカテゴリ→内容→挿入位置を選ぶ新規入力モーダル。S11はC01内の写真機能とし、専用の振り返り画面は作らない。

理由：旅行詳細を中心に、計画・旅行中の記録・振り返りを継続できるようにするため。

残件は閲覧用共有リンクの期限・失効・再発行・発行権限、個別競合時や削除調整時のUX等。日単位の並び替え排他、メモ・写真の並行変更、非公開旅行の写真非表示、招待URL複数人利用・S03遷移は確定済み。

残るUXは [screens.md](./screens.md)、DBの技術設計・migration前の残件は [db-implementation.md](./db-implementation.md#9-未決定事項) を参照する。
