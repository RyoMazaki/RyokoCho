# 設計判断の記録

## 2026-09-27：公開制御・旅程データの方針統一

状態：以下の5項目は確定。非参加者閲覧等は、同日後続の画面設計の決定を反映した現行内容として記載する。DB・アプリへの実装は未実施であり、今回の変更はドキュメントとDB実装設計に限る。

参照する役割は、[product.md](./product.md) がプロダクト思想、[requirements.md](./requirements.md) がユーザー向け仕様、[data_model.md](./data_model.md) が論理モデル、[db-implementation.md](./db-implementation.md) が具体的DB設計である。本書は判断と理由を記録し、未決定仕様を補完して確定するためには使わない。

### 1. 非参加者の旅行閲覧をMVPで提供する

旅行メンバーは閲覧・編集できる。非参加者はログイン不要で、メンバーと同じ旅行URLのS05・C01を閲覧できるが編集できない。閲覧のためにメンバー登録しない。参加情報は人数のみとし、S08・表示名・プロフィール画像・メモ・非公開写真は公開しない。

理由：旅行の共有とメンバーの共同編集を分離し、参加者の情報を保護しながら閲覧を可能にするため。

未決定：旅行単位の公開範囲の値・管理方法、公開設定者、閲覧URLの配布UI。ログイン要否・共通URL・MVP採用・人数のみ・メモ非公開は確定済み。公開旅行一覧・検索は追加しない。

### 2. 写真単位の公開可否

`itinerary_photos.is_public boolean NOT NULL DEFAULT false` を採用する。

- `false`：旅行メンバーのみ閲覧可能。
- `true`：非参加者にも閲覧を許可できる写真。無条件公開ではない。

理由：写真ごとに共有対象を制御し、初期状態で意図せず公開しないため。旅行を基準にしたメンバー権限は維持し、写真の非参加者閲覧は別途判定する。

未決定：旅行の公開制御との関係、非公開旅行の写真単独公開、公開設定を変更できる人（アップロード時も含む）、写真編集の具体的範囲と権限。非参加者閲覧はログイン不要。サムネイルはS05で旅行閲覧条件に従って表示する。RLSとStorageは同じ閲覧条件を適用し、公開閲覧を編集権限へ広げない。

### 3. 旅程日は原則として旅行期間内

`trips.start_date <= itinerary_items.date <= trips.end_date` を原則とする。DBの単純なCHECKでは保証せず、MVPではアプリケーション側で検証する。

理由：親テーブルの日付を参照するルールであり、単一行のCHECKとして扱わないため。

未決定：旅行期間短縮時に既存の範囲外アイテムをどう扱うか。自動削除・日付移動・拒否などを独断で採用しない。

### 4. 時間の整合性はDB CHECKで保証

| time_type | exact_time | time_period |
| --- | --- | --- |
| `exact` | NOT NULL | NULL |
| `period` | NULL | NOT NULL |
| `none` | NULL | NULL |

理由：単一行で保証でき、直接API書き込みを含め不整合を防げるため。アプリ側かDB側かという古い未決定記述を廃止する。時間帯の値や海外旅行の時刻表現などは、この決定には含まない。

### 5. action categoryを追加しない

categoryは `place` と `transportation` を維持する。`place` は場所、その場所で行うこと、滞在中の行動を含む。例は東京駅、ホテルに荷物を預ける、昼食、清水寺を観光する。

理由：場所とその場所での行動を現行モデルで表現でき、独立categoryやテーブルは必要ないため。

### 解消した不一致と残る判断

要件の非参加者閲覧とモデルの「許可するか未決定」を統一した。写真公開は写真単位の確定カラムに統一し、公開粒度や既定値を未決定から除外した。モデル前半と後半で異なっていた期間検証と時間CHECKの記述を統一し、行動が独立categoryに見える要件を修正した。

残るUXは [screens.md](./screens.md)、DB設計の未決定事項とmigration前の判断事項は [db-implementation.md](./db-implementation.md#9-未決定事項) と同文書末尾に集約する。公開条件や設定者などの残件があっても、今回確定した機能の必要性・型・検証方針は未決定へ戻さない。

## 2026-09-27：画面構成・保存単位・招待と公開情報の確定

状態：[screens.md](./screens.md) の決定を要件・論理モデル・DB設計へ反映。実装・migration適用は未実施。

### 画面構成

S01・S02・S04・S06は独立ページ、S03・S05・S07もページとして扱う。S07は初回プロフィール入力と通常編集で共用する。S08・C01はモーダル、S09はS05の編集状態、S10は上下の＋からカテゴリ→内容→挿入箇所を選ぶ新規入力モーダル、S11はC01内の写真機能とする。

理由：旅行詳細を中心に計画・旅行中の記録・振り返りを行い、不要な独立画面を増やさないため。

### 保存単位とメモ

メモは `itinerary_items.description` の任意の単一共有テキスト。既存メモ・既存アイテムへの写真アップロードはC01で即保存する。新規アイテム・メモ・写真はモーダルの「保存」で合わせて登録し、「キャンセル」では登録を確定しない。既存旅程の基本項目・順序等はS05の「更新」で保存する。

理由：最新の操作方針に合わせて保存単位を分けるため。一括更新や編集破棄で即保存済みの内容を巻き戻さない。DBとStorageが一括コミットできるという意味ではなく、途中失敗・補償が必要。

未決定：メモ送信の契機、編集開始条件、既存未保存変更と新規挿入の整合、更新範囲、同時編集・部分失敗時のUX。

### 招待と初回入力

MVPの招待は作成者のみがS08から行い、参加は招待URLから行う。参加時は認証ユーザーを識別する。S07で初回プロフィールを作成し、招待経由なら認証・初回入力後に参加処理へ戻る。閲覧URLを開くだけでは参加させない。

理由：ログイン不要の閲覧と、編集権限を得る参加を区別するため。通常のメンバーroleは増やさず、招待・旅行削除の作成者判定には `trips.created_by` を使う。

未決定：認証方式、招待URLの有効期限・再利用・失効・転送可否・参加確認・配布UI。

### 公開取得と参加者表示

非参加者はS05・C01をログイン不要で閲覧し、人数だけを確認できる。S08・メモは非公開とする後の補足を優先する。旅行メンバーにはS08で同じ旅行の参加者の表示名・任意画像を表示する。

理由：GUIで隠すだけでは情報を保護できないため。DB設計ではメモを含まない公開取得、件数のみの取得、旅行単位のプロフィール取得と画像配信を分離する。これらの技術案は採用済みのプロダクト仕様を変更するものではない。

今回の修正対象はdocs内。ルートの [AGENTS.md](../AGENTS.md) に残るログイン要否等の古い未決定記述も将来の更新対象であり、本記録と画面設計に反映したユーザーの確定事項を再度未決定として扱わない。
